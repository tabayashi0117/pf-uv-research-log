# g-patrol — 研究の親の巡回(全 G、2026-10-21 ユーザー指示)

経緯と設計の正本:(研究ノート: `相談回答_親エージェントの自律継続の強制_2026-10-21.md`)。
ユーザーがこれまで手で出していた 4 種の指示 —「いまできることを洗い出して着手」「大局的なアプローチ・全体戦略の見直し」「計算ジョブの現状の確認」「投入待ちなら他マシンの資源の確認」— をこの手順が代わりに出す。**指示を待たずに、毎回上から全部を回す。**

引数:対象の (研究ノート: `_orders`) の路(例 (研究ノート: `_orders`))。無ければ、このセッションが `ready_claim.py claim` した (研究ノート: `_orders`)(`.ready_owner` にこのセッションの session_id がある所)。G の root はその親フォルダ。

## 0. 前提の確認(毎回、1〜2 手)
- 旗 `<_orders>/NO_NEW_ORDERS` があれば巡回はチェックポイント(6.)だけ — 締め・ユーザーの停止の指示・週次枠の上限。
- **定期巡回**:`python (研究ノート) status <_orders> <session_id>` で `.patrol_armed` を見る。このセッションの行が無い・6.5 日を超えたら、`CronCreate`(cron `"7 * * * *"`、recurring true、prompt `"/g-patrol <_orders の路>"`)で 1 時間ごとの巡回を張り、`patrol_mark.py arm <_orders> <session_id> <cron の ID>`。`CronList` に既にあれば張り直さない(二重に張らない)。
- 長時間の自律運転の間は `request_keep_awake`(until `session_idle`)を 1 回。
- session_id は SessionStart フックの `[session-id]` の表示(分からなければ `.ready_owner` の自分の行)。READY.md が無い G は雛形 `rules/templates/READY.md` から作り、`ready_claim.py claim` する。

## 1. 計算ジョブの現状(ユーザーの「計算ジョブの現状を確認して」)
- G の (研究ノート: `RUNNING.md`) の全行を、遠隔は `python (研究ノート) ps`(出力が大きいので自分の G の行だけ抜く)、自機は PID(`tasklist` / `ps`)で確かめる。「見に行く時刻」を過ぎた行は必ず中身(STATUS.md・`projection.json`・out.log の末尾)を見る。
- 完了したもの:`dispatch.py get <名> --all --out <ジョブ>/_got`(commit は `result.json` だけ)→ 判定文を当てる体(元の回収の体の再開か、書き下しの型 の新しい体)を出す。壁時計で止まったものは README の手順で relaunch(jobgate を通す)。異常(死んだ・進まない・`PROJECTION_OVER`・`watcher_error`)は原因を 1 行で STATUS に書き、直すか止める(停止は PID 指定だけ)。
- **完了で親を起こす監視**:走っているジョブに監視が無ければ張る — `Bash` の `run_in_background` で「`result.json`・`DONE`・`FAILED` のどれかが出るまで 10 分おきに確かめる」待ち受け(遠隔は `dispatch.py get <名> --file result.json --out <一時>` を試す;終わりの全ての状態で抜ける)。終われば通知で親が起きる。

## 2. 投入待ちのジョブ(ユーザーの「投入待ちなら他マシンの資源を確認して」)
- RUNNING.md・READY の投入待ちの行ごとに、`dispatch.py free`(実負荷つき)と自機の負荷(コア・GPU)を見て、空いた計算機に割り当てる。`python (研究ノート) --check <名>` が PASS なら投入し、1〜2 分後に PID・out.log で起動を確かめ、RUNNING.md に登録し、1. の監視を張る。FAIL の理由が効率の監査なら監査の体(雛形 `rules/templates/EFF_AUDIT.md`)を出す。GPU は 1 枚に 1 本、自機の CPU は物理コア − 2 以内、他の G のジョブは止めない。

## 3. READY の発注
- `ready` の行は全て発注して `running` に(族単位・類 C を先に・消費者を先に・合同監査の規律の範囲で;発注文は (研究ノート: `_orders`) に保存し、必須行はフック require-outlook が検査する)。
- `blocked` の行は、待っているもの(体・ジョブ・監査・計算機)が解けたかを確かめ、解けていれば `ready` に上げて発注する。終わった行は消す。

## 4. 補充(ユーザーの「いまできることを洗い出して着手」)
- 生きている体(このセッションが起動・再開してまだ戻っていないサブエージェント)が 3 本未満で、3. の後も `ready` が 0 行なら、**補充のサイクル**を回す(冷却なし):READY に「補充のサイクル」の行を running で足す → 計算ジョブ以外でいま着手できる手を各レーンの STATUS・塊台帳・READY の blocked/defer・PROVED の candidate・FAILED の再挑戦条件・承認待ちから洗い出してタスク表((研究ノート: `03_worklog`) か (研究ノート: `worklog`) に `<日付>_補充_タスク表_S<n>.md`)→ 監査の型 1 体の一度きりの独立監査 → 判定 OK・FIX の行を全て発注、DROP は出さない、ユーザー判断が要る行は推奨案つきで承認待ちに → 行を消す。雛形は G の (研究ノート: `_TEMPLATE_replenish.md`)、無ければ `rules/templates/REPLENISH.md`。前回のタスク表と監査で DROP した手は再掲しない(再挑戦条件が満たされたときだけ)。
- 監査が「着手できる手 0 本」を返したら、それを記録して 5. へ。

## 5. 停滞の検出と大局の見直し(ユーザーの「大局的なアプローチ・全体戦略の見直し」)
次のどれかで発火する:(a) `.patrol_log` の直近 6 時間の行の「台帳」の値(STATUS の 1 行目の残り台帳の本数)が全て同じで、物差し 6″((a) 条件の強化・削減、(b) 閉じた方式の記録、(c) 類 C の数値の判定)も 6 時間増えていない;(b) 補充のサイクルが 2 回続けて着手 0〜1 本;(c) 同じ台帳の行で方式の閉鎖(FAILED)が 3 本続いた。
- 発火したら、親がテンプレート C で設計をやり直す:閉じた方式の共通点を 1 行 → 消費者の側の字面を先に照合 → 新しい十分条件の候補表(有望な順、各候補に成算 2 本)→ 主標的・目標の置き方の見直しの要否。設計メモは worklog に日付つきで、STATUS の 1 行目から指す(`rules/研究運用.md` の「研究の型」6.・規律 6′)。
- 設計を 監査の型 1 体の監査(設計の監査 — 網羅性・難しさの所在・消費者の字面)に出し、合格した角度を発注する。主標的の置き直し・STATEMENT の変更などユーザー判断が要る点は、推奨案つきで (研究ノート: `承認待ち.md`) に 1 行、ユーザーにも報告する(`rules/研究運用.md` の大きな進展の通知の 6. に当たれば通知)。
- 基礎研究の行(規律 6′〜6‴)は止めない:候補表から有望な順に出し続ける。ユーザーが巡を止めた行は、その判断の範囲を守る(成算なしの確定と大局の別の道は出してよい)。

## 6. チェックポイントと記録
- 成果 1 単位か 60 分ごと:STATUS(と兼務するレーンの STATUS)・READY・RUNNING を書き換え、明示のパスで commit・push(同期は `git fetch origin master && git rebase --autostash origin/master`;体が tracked ファイルを編集中なら autostash を使わず先に commit して merge)。時刻は書く直前に `date +%H:%M`。
- 週次枠:`get_usage`(ccd_session_mgmt)を 1〜2 時間ごとに見て、設定の上限(既定 99%)に達したら旗 `NO_NEW_ORDERS` を置いて締めに入る。
- **最後に必ず記録する**:`python (研究ノート) log <_orders> <session_id> "台帳=<STATUS 1 行目の本数の要約>|体=<生きている体の数>|ジョブ=<稼働・待ちの本数>|着手=<発注・投入した名前 / 0 なら着手できない理由(全行の待ち・空き計算機 0・補充の監査が 0 本)>|次=<次に起こすもの:定期巡回・ジョブの監視・体の戻り>"`。この記録が無いと Stop フック require_autonomy.py が停止を拒否する。
