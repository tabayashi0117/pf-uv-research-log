## セッション運用(トークン規律)

蓄積型の研究フォルダでは、毎セッションの読み直しと検証済みの再検証がトークン消費の主因になる。全研究テーマで次を守る。

1. BOOT.md 方式: 各テーマ直下に `BOOT.md`(起動シート)を置き、起動時に読むのはこれだけにする。総括・過去稿・台帳は通読せず、他ファイルは必要な節だけ offset/limit で開く。無いテーマは最初のセッション終了時に作り、以後セッション終了時に更新する(引き継ぎの正本は BOOT.md。総括の書き換えは大きな節目だけ)。
   - 書き換え型: 項目の連番追記やセッション履歴を足さず、毎回「現在の状態」に書き換える。履歴は worklog へ。
   - 8KB 目安・12KB 上限。超えたら次セッションの最初の仕事として圧縮する(膨れると起動時に読めなくなる)。
   - 構造は固定: 現在地 3 行 / 確立済み事実表 / 開タスク / 罠 / ファイルマップ / 作業中 / 運用規則。`STATUS*.md` を持つテーマ(「研究の型」1.)では、現在地・開タスク・作業中は STATUS に置き、BOOT はその所在を 1 行で指す。事実表は「ID + 1 文 + 出典」で最大 15 行、溢れる分はテーマ直下 `FACTS.md`(追記型)へ移して BOOT には ID 一覧だけ残す。作業中表の完了行はすぐ消す。
   - ファイルマップ節は必須: 冒頭にテーマ root のフルパスを 1 回書き、以下は相対パスと 1 行要旨(パスの推測による誤発注を防ぐ)。稿が 30 本を超えたら `91_ファイルマップ.md` に分離する。
2. 確立済みの再検証をしない: 検証済み(verifier-backed / promoted / 実測確認済み)の結果・手順・調査は公理として使い、再証明・再監査・再実行・「念のため確認」をしない。
3. サブエージェント監査: 独立監査は明確な昇格候補ができたときに行う。体数の上限は無く、独立な候補が複数あれば並列でよい。プロンプトには監査対象の新規主張本文と「確立済み事実表(再検証禁止の公理)」を同梱し、対象以外を読ませない。報告形式は 7.。
4. kill-check 先行: 長い解析・実装の前に、小さな実験・有限模型で安く殺す。同じ論法で 3 ラウンド停滞したら打ち切り、FAILED(または相当の記録)に書いて転進する。
5. 数値実験・計算: 実行するのは新規スクリプトだけ(検証済みスクリプトは再実行しない)。例外は、監査人の独立な再実装による再現(推奨)、入力・コード・環境の hash が変わったときの互換性確認、公理の読み方に疑義があるときの一次資料 1 手。
   - 「5 分以内」は対話の計算に限る。5 分を超える計算は (研究ノート: `<名前>`)(`ORDER.md`・`run.py`・`STATUS.md`・`result.json`・`out.log`)に置いて `nohup` で起動し、(研究ノート: `RUNNING.md`) に PID・コア数・見込み時間・回収コマンドを登録する(終了時に削除。sleep の監視ループは回さない)。
   - tier: C0 = 5 分以内(対話)/ C1 = CPU 2 時間・RAM 16GB 以内(登録のみ)/ C2 = 12 時間・GPU 1 枚以内(登録 + BOOT 作業中に記載)。それ以上・有料クラウド・200GB 超・OS/ドライバ変更は承認が要る。並列は `OMP_NUM_THREADS=1`、合計コア数は物理コア − 2 以内、GPU ジョブは同時 1 本。GPU(float32)は篩い分け・探索専用で、確定計算は CPU float64 か区間演算。
   - `result.json` に seed・ライブラリ版・環境・入力 hash・結論(PASS / COUNTEREXAMPLE / INCONCLUSIVE)を記録する。共有の検証済み核は (研究ノート: `lib`)、キャッシュは (研究ノート: `cache`)(git 管理外)、小さな共有数表は (研究ノート: `tables`)。
   - 切断・格子は 3 段階以上並べ、最後の 2 段で不変を示す(小さい切断の 1 点は証拠にしない)。
   - 早期打ち切り: 5 分超のジョブは起動前に `STOP_RULES.json`(冪の安定・仮説の分離 Δχ²・外挿値の信頼区間・反例確定・精度到達のいずれかと最低データ量)と `stop_adapter.py`(partial → 表)を置き、(研究ノート: `early_stop.py --watch --pid`) を常駐させて、規則を満たした時点で止める。タスクは情報量順(梯子の粗い段・全セルを先に、seed は層化)、partial は短い間隔で保存。規則は途中で緩めない(緩めたくなったら結果を捨てて別ジョブで再起動)。規則で止めた計算は完走と同格で、残りを回さない。
   - **計算ジョブの起動前の規則(2026-10-20 ユーザー指示、(研究ノート: `01_新井プログラム継承`) の全 G・全エージェント、永続)**:経緯 — G4 の 300 本の集計で、判定の札のある 207 本のうち INCONCLUSIVE が 80 本(39%)、その約 6 割が壁時計・データ不足・課題の失敗で止まった型だった;また長いジョブが計算機を長く塞ぎ、重要なジョブが遅れることが多かった(記録 (研究ノート: `2026-10-20_計算ジョブ_INCONCLUSIVE集計.md`))。ジョブを包装する体(ORDER.md を書く体)と投入する親は、ORDER.md に次を書く(雛形 `rules/templates/JOB_ORDER.md`):
     - (R) 資源の予算の行「資源: コア時 … ・GPU 時 … ・壁時計 … h ・計算機 …」。
     - (a) 「検出力: 要る n = …(smoke の 1 配位あたりの分散から、起動前に固定した判定の帯を割るのに要る数)/ 計画の n = …」— 届かないなら点・段・判定量を減らすか変えてから投入する。

     - (E) 「## 効率の見直し」の節に 5 項目を 1 行ずつ:**最小の計算**(判定に要る最小の量・逐次の止め方・既に答えの出た部分を再計算しない)・**アルゴリズム**(推定量の分散の削減・解法の前処理・再利用・小さい格子や粗い段で先に決める)・**並列**(飽和するコア数・GPU の適合・空いた計算機)・**精度**(判定に要る精度に対して過剰でないか)・**並び**(情報量の順)。
     - (A) 大きなジョブ(コア時 ≥ 24・GPU 時 ≥ 4・壁時計 ≥ 8 h のどれか)は、包装と別の体(書き下しの型、雛形 `rules/templates/EFF_AUDIT.md`、同じ族はまとめて 1 体)の効率の監査の PASS を受け、「効率の監査: <発注名>(<記録>)PASS」の行を入れてから投入する。
     - (c) result.json の判定が INCONCLUSIVE のとき `inconclusive_reason`(`wall_clock` / `few_data` / `task_failed` / `middle_band` の 1 語 + 1 文)を `run.py` が必ず書く。(d) 1 つの問いを複数の計算機・部に分けたら、部の result.json は `"verdict": "PART"` だけ、判定は ORDER.md に名前を書いた結合のスクリプトの出力だけが持つ。
     - **追加(2026-10-20 ユーザー承認「実施してください。全Gに適用してください。」、全 G、永続)**:経緯 — G3 E05 のジョブ 310(MPS)は、見積もり 3〜4.5 h に対して 20 h の壁時計に当たり、INCONCLUSIVE(REACH)になった。判定に要る最上段のセルを本番の仕様で試さず、そのセルが最後に回る順番で、計算機の実負荷を見ず、早期停止の常駐が無言で落ちていた。それでも済んだ段の値は答えの向きを出していた(記録 (研究ノート: `2026-10-20_親_計算ジョブのINCONCLUSIVEの振り返りと改善案.md`))。上の (R)〜(d) に次を足す。
       - (F) **決め手のセル**:ORDER.md に「決め手のセル:…」(判定文が実際に読むセル・課題)を列挙する。そのうち最も重い 1 つを、本番の仕様・本番の計算機(無理なら同じ型の機械、その旨を書く)で 1 単位(掃引 1 回・軌道 1 本など)回した実測を「決め手の smoke:…」の行に書く。(b) の壁時計はこの実測から出す。別ジョブの数字の流用は不可。
       - (G) **段階つきの判定文**:判定文は「最終の札」と「到達した段での暫定の札」の 2 段で書く(収束の検査は到達した最上の 2 段で)。最上段が揃わなければ何も言わない全か無かの形は禁止。判定文が読むセルが PLAN に全てあることを、包装の検査で機械的に照合する。

       - (I) **走行中の見通し**:jobkit が partial のたびに、決め手のセルの完了見込みを STATUS.md と `projection.json` に書く。見込みが壁時計の上限を超えたら `PROJECTION_OVER` を立てる。早期停止の常駐が例外で止まったら heartbeat に `watcher_error` を書く。親は RUNNING.md の各行に「見に行く時刻」(見積もりの 1.5 倍)を書き、その時刻に 1 回確かめる。
       - (J) **実負荷**:`dispatch.py free` はホストの実際の CPU 負荷も表示する。実負荷が上限を超えるホストへの投入は警告する。

   - プロセスの停止は PID 指定だけ(ルート CLAUDE.md「作業スタイル」)。
6. 参照の最小化: 作業に要るファイル・節だけを参照する。`grep -n` で位置を特定し、offset/limit(または `sed -n`)で必要行だけ開く。フォルダの通読、背景把握のための総括・過去稿、関連しそうなファイルの予備的な読み込みはしない。サブエージェントのプロンプトには「読んでよいファイルと節の一覧」と「必要な確立済み事実の要約」を同梱し、それ以外(通読・ROADMAP・進捗総括・他テーマ)を読ませないと明記する。ただし発注前に、前提として書く行を `grep -n` で 1 手確かめる。
7. サブエージェント運用(親の側): ワーカー・監査者の作法(git を実行しない、ヒアドキュメント禁止、`_inbox` の完成文と `F-?`、worklog の骨組み先行・§0 を 10 分以内・`DONE`、1 回 300 行、対話計算 5 分、`result.json`、再監査等級の明記、報告形式、停止は PID 指定)は (研究ノート: `agents`) の型定義(`監査の型.md` の「作法」)が正本。型で起動しない経路(他のエージェント・`general-purpose` など)では、発注文でその節を読ませる。親の規則は次のとおり。
   - 報告は節構成で指定する: 判定表(1 項目 1 行、200 字以内)+ 総合 5 文 + 成果物パス。命題全文・数値表・残タスクの詳細はファイルに書かせ、チャットに再掲させない(親のコンテキストを圧迫する)。
   - 利用枠切れ(429)で消えた体のファイルは、親が WIP として commit する。ワーカーは自分が新規作成したファイル(worklog・experiments・新規稿)だけを書き、親が絶対パスで commit する。
   - (研究ノート: `<agent>.<台帳名>.md`)(例 `w12.PROVED.md`・`w12.FAILED.md`・`audit07.AUDIT.md`・`audit07.PATCH.md`)は台帳末尾にそのまま連結できる完成文。親は `cat` で連結するだけで、書き直しが要る断片は差し戻す。監査の処方は `PATCH.md` に「対象ファイル / old(逐語)/ new / 理由」で書かせ、稿の作成者・親・反映係が機械的に適用する(稿修正ワーカーは置かない。台帳整理は 1 体に集約してよい)。
   - 識別子: 新規稿の `NN_` 番号は発注時に親が予約する。FAILED の F 番号は予約しない(inbox には `F-?`、親が連結時に採番)。
   - 正本は 2 つだけ: 主張は `PROVED.md`(ID・命題文・格付け・証明と監査記録の所在)、監査の判定は監査記録ファイル。EVIDENCE はオッズと判断の反転の経緯、NOVEL は ID・1 文・先行研究・リンク、REGISTRY は経路の状態、BOOT の事実表は「ID + 1 文 + 出典」だけ。命題全文を 2 か所以上に書かない(多重転記が最大のトークン消費源だった)。
   - 稿の冒頭ブロック(必須): `主張 / 仮定 / 非主張 / 格付け / 監査記録 / 訂正注記`。発注の公理表はこのブロックを grep して作り、発注文の冒頭に「既解決チェック」(PROVED/FAILED の該当 ID を grep)を置く。読んでよい範囲は行番号でなく見出し文字列で指定する。
   - 訂正稿を書いたら、対象稿と影響を受けた監査稿の冒頭ブロックに 1 行注記(日付・出所・無効範囲)。verifier-backed 稿は本文を改変せず注記だけ。
   - 再監査等級: 監査人は報告末尾に S0(記号・算術のみ → 反映報告で verifier-backed)/ S1(証明段の変更 → 差分監査)/ S2(量化子・定義域・主張の変更 → full fresh audit)を書く。親は反映後に grep で件数を照合してから等級どおりに発注する。依存関係のある 2〜3 稿は 1 体で合同監査。監査は「次の一手の発見」にも使ってよい。監査人の処方も検算する。
   - 発注文・監査プロンプトはテンプレ((研究ノート: `TEMPLATES`))から作り、完成形をテーマ直下 (研究ノート: `<名前>.md`) に保存して、プロンプトは「これを読め」の数行にする(再発注が安くなる)。
   - 起動した agentId と担当は STATUS(無ければ BOOT.md)の「作業中」節に記録し、完了行はすぐ消す。枠切れ後は `SendMessage` で同じ agentId の再開を試み、セッションを跨いで無理なら (研究ノート: `_orders`) から再発注する。**前のセッションの体は新しいセッションからは再開できないことが多い**(2026-10-19 改訂):`SendMessage` は 1 回だけ試し、届かなければ前の体の稿・発注文・ジョブの `ORDER.md` を「読んでよい範囲」に入れた新しい体で出し直す(S1・独立確認は 監査の型、回収と書き下しは 書き下しの型;判定文は起動前に固定したものをそのまま当てさせる)。そのため STATUS の作業中には、agentId に加えて「回収の先」(稿・発注名・ジョブ名)を書き、締めでは agentId だけの一覧を残さない。
8. 成算の先行(雑な計算): 新しい標的・命題・発注・閉鎖判定・長い数値実験の前に、独立な雑な推論を 2 本以上(次元解析、摂動・1 ループの値、玩具模型、有限模型の 5 分以内の数値、物理的直感、既知の類似問題からの外挿など)で「成立しそうか」「どの冪・定数で」「どこで破れそうか」を出す。
   - テーマ直下の `成算.md`(追記型)に「ID / 標的 / 推論 1 / 推論 2 / 判定(成算あり・なし・条件付き)/ 破れる条件 / 日付」で残す。BOOT の開タスクと STATUS の「次の 3 手」は `成算.md` の ID を引く(成算の無い標的は書けない)。
   - 2 本とも否定、または 1 本も作れないなら厳密な作業に進まない(標的を再設定するか、雑な計算そのものを発注する)。
   - 雑な計算は「値であって上下界ではない」(E05 の T88)。格付けに混ぜず、`成算.md` にだけ載せる(PROVED/FAILED には書かない)。
   - 発注文には必須節「## 成算(雑な計算 2 本以上、`成算.md` の ID)」を置く。ワーカーは §0 に雑な見通しを 10 分以内で書き、否定なら厳密化に進まず親に問う。監査の発注には「成算の検算(推論の向きと冪)」を 1 項目入れる。
   - 例外は値を持たない作業(well-definedness の基盤整備など)だけで、その場合も発注文に「成算不要: 理由」を 1 行書く。
   - 数値事実の照合: 数値事実は `data/ledgers/NUMERICS_FACTS_E05.md`(NUM 番号、1 行 1 事実、応用先の G 付き)に集約されている。成算・命題・発注文・閉鎖判定の前に、自 G の行と応用先に自 G が挙がる行を `grep -n` で引き、数値が否定する向きの命題は成算なしとして立てない(数値は証明の代替ではないが、無視して逆向きを証明しようとしない)。発注文の「## 成算」節(または「成算不要:」の直後)に「数値事実の照合: NUM-… / 該当なし」を 1 行書く。監査の発注には「NUMERICS_FACTS との整合」を 1 項目入れる。
   - Claude Code では PreToolUse フック (研究ノート: `require-outlook.sh`) が、(研究ノート: `04_研究`) 配下の (研究ノート: `*.md`) を指す `Agent` 起動で「## 成算」節(または「成算不要:」行)と「数値事実の照合」行を検査し、無ければ拒否する。(研究ノート: `01_新井プログラム継承`) 配下の発注文はさらに「既解決の確認: grep 語 … → #番号 / 該当なし」行も検査する(2026-10-12 ユーザー指示。7. の「既解決チェック」を発注前に必ず実行させるため)。フックを読まないエージェントは手で守る。

## モデルと同時起動

- サブエージェントは (研究ノート: `agents`) の型を `subagent_type` に指定して起動する(Agent ツールの `model` 引数では effort が変わらない。型はセッション開始時に読み込まれる)。

## 進捗の指標と並列度の規律(2026-10-12 ユーザー指示。全 G・全マシン・全研究セッション・全エージェント)

経緯: G4 S33 で、名指し(未証明の条件の名前)を 1 本解くと新しい名指しが数本出る帰着を、1 本ごとに「書き下し → S2 → S1 → 照合 2〜3 本」で回した。verifier-backed の補題は約 20 本増えたが、目標命題(段階 1a)の残りの条件は 17 本 → 20 本超で減らなかった。大量のバックグラウンドタスクを走らせても進捗しない状態を、全研究で防ぐ。記録は `rules/規約の改訂履歴.md`。

1. **残り台帳**: 各 G(レーン・テーマ)は、いまの主標的(目標命題)を成り立たせるのに残っている未証明の条件(名指し・予想・未照合の読み)の台帳を 1 ファイル持つ(置き場所は G の `STATUS*.md` から 1 行で指す)。各条件を次の 3 類に分ける。
   - 類 A:字面の照合・読みで済む。
   - 類 B:本物の解析・評価が要る。
   - 類 C:偽かもしれない(値の見積もりで破れる懸念がある、または否定済みの経路がある)。
   BOOT/STATUS の現在地の 1 行目に「残り台帳: C n 本・B n 族・A n 項目」を書き、チェックポイントごとに更新する。**進み具合はこの本数で測る。verifier-backed の本数・監査の本数・発注の本数は進捗に数えない。**
2. **発注の必須行**: 発注文に「台帳: 閉じる番号 … / 差し引き −n」の 1 行を書く。帰着だけで本数が減らない発注は出さない。台帳に直接効かない作業(照合・数値・監査・機械作業)は「台帳: 対象外(理由と、どの番号の判定に使うか)」と書く。フック `require-outlook.sh` が (研究ノート: `04_研究`) 配下の発注文で検査する。
3. **類 C を先に当てる**: 偽かもしれない条件の kill-check(成算・小さな数値・字面の照合)を、その条件に依存する書き下しより先に行う。類 C が否定なら、その経路の書き下しを止めて経路を組み替える。
4. **作業の単位は名指しの族**: 同じ機構で閉じる条件はまとめて 1 体に渡す。書き下しの体には予算 4〜8 時間と、関係する稿全体の読む範囲を与え、範囲の外の照合も自分で行わせる(別の発注に回さない)。新しい名指しを残してよいのは「予算内で解けないと示せた場合」だけで、その理由を稿に書く。**1 段だけ帰着して名指しを外に出した稿は、成果として扱わない**(台帳の本数で評価する)。
5. **監査は塊ごと**: 小さな帰着ごとに S2・S1 を出さない。台帳の行(目標命題の 1 つの仮定の塊)が閉じた時点で、関係する稿をまとめて合同 S2(1 体)にする。S1 は元の監査人を再開する。照合だけの体は、監査か次の族の書き下しに吸収する。
6. **停滞の検出**: 2 チェックポイント続けて台帳の類 B・C の本数が減らなければ、親が設計(テンプレート C)をやり直し、BOOT 現在地の 1 行目に「設計やり直し 日付・理由」を記録する。**閉じに向かう行**(残りが照合と既知の型の評価で、閉鎖が見えている行)では、やり直しの間は新規の発注を止める;3 回続けば経路を閉じ(FAILED に記録)、目標の置き方の見直しをユーザーに報告する。**基礎研究の行**(STATUS で「基礎研究」と宣言した行。例:G4 の領域 (II)・(III))は下の 6′.〜6‴. に従い、発注を止めない。〔2026-10-17 ユーザー承認で改訂。旧:「減らなければ新規の発注を止める」を全ての行に当てていた。〕
   - 6′. **基礎研究の行は止めずに設計し直す**:停滞を検出したら設計のやり直し(テンプレート C:閉じた方式の共通点を 1 行、新しい十分条件の候補表を有望な順に)を義務にし、**その候補表から有望な順に発注を続ける**。止めるのは、候補表の全ての角度が試されたか、残りの全てが成算 1 割未満になったときだけで、そのときはユーザーに報告して目標の置き方を相談する。
   - 6″. **進み具合の物差しを足す**:基礎研究の行では、行の本数に加えて (a) 条件付きの定理の条件が強くなった・減った(verifier-backed の条件付き定理の形で)、(b) 閉じた方式とその共通点が系譜・FAILED に記録された、(c) 類 C の数値の判定が出た、の 3 つでも測り、STATUS の推移の行に書く。行の本数が動かないこと自体を停止の理由にしない。
   - 6‴. **相談回答・設計メモの候補表を常設の発注の待ち行列にする**:その G の最新の相談回答(「まだ試していないこと」の表)か設計メモの候補表を待ち行列とし、体が戻るたびに上から起動する。表は数体が戻るごとに書き直す(閉じた角度を消し、新しく見つかった角度を足す)。
   - 3.〜5. と「サブエージェントの粒度と合同監査」(族単位の発注・合同監査・1 段の帰着は成果に数えない・同時の体数の目安)は基礎研究の行でもそのまま守る。
   - **ユーザーの直近の明示の指示は、この節の一般の規律より優先する**。両者が衝突すると気づいたら、黙って一般の規律を当てずにユーザーに確かめる(経緯:2026-10-16 G4 S37 で 6. を当てて新規発注を止め、ユーザーの「着手できることが尽きるまで実施」の指示を上書きした)。
7. **報告の正直さ**: セッション報告と進捗ファイルに「残り台帳の本数の推移(開始 → 終了)」を必ず書く。増えたなら増えたと書く。分割が多い理由を、本質的な難しさ(評価の本数そのもの)と手順の無駄(体の数・監査の重ね方)に分けて申告する。

## サブエージェントの粒度と合同監査(2026-10-15 ユーザー指示。全 G・全マシン・全研究セッション・全エージェント)

経緯: G4 S35 で、類 A の照合 1〜2 項目・小さな kill-check・稿ごとの S2・別の体による S1 を細かく発注し、同時に 8〜9 体を動かした。ユーザーから「バックグラウンドタスクを立ち上げすぎてトークンを大量消費している。監査は合同監査に、サブエージェントにはまとまったタスクを渡す。小さいタスクに切り分けるとすぐに利用枠がなくなる」と指示された。上の「進捗の指標と並列度の規律」3.〜5. の運用の具体化で、矛盾したらこちらが優先する。

1. **まとまったタスクを渡す**:1 体の発注は「名指しの族」を単位にし、予算は 4〜8 時間を基本とする。照合(類 A)・類 C の kill-check・5 分以内の数値は、それを使う書き下しの体の任務 (0) に吸収し、**単独の体として発注しない**。単独で出してよいのは、それだけで行の判定が決まり、かつ同時に書き下す族が無いときだけ。
2. **監査は合同に**:S2 は台帳の行(塊)が閉じた時点で、関係する稿を全てまとめて 1 体に渡す。稿ごとに S2 を出さない。S1 と「監査人が自分で書いた補題の独立確認」は、新しい体を立てず、元の監査人か稿の著者を `SendMessage` で再開して 1 体で行う(著者は監査人と別の体なので独立確認になる)。セッションを跨いで再開できないときは、監査稿・稿を読む範囲に入れた新しい体で行う(7. の 2026-10-19 改訂)。
3. **同時に動かす体は少数に**:重い体(Opus)の同時稼働は、1 セッションあたり**目安 4 体程度**(**G4 は除く** — 2026-10-17 ユーザー指示で G4 は体数の制限を撤廃、必要なだけ並行して起動する;「モデルと同時起動」の例外)。新しい発注の前に、稼働中の体へ `SendMessage` で範囲を追加できないか、戻ってきた体を再開して続きを渡せないかを先に検討する(既に読んだ文脈を使い回すほうが安い)。
4. **戻ってきたらすぐ補充しない**:体が戻っても機械的に次の体を出さず、残りの名指しを族にまとめてから発注する。報告の「残タスク」が小さな項目の列挙なら、親が族にまとめ直す。
5. **ワーカーの側**:範囲外の照合も予算内なら自分で行い、親に小さな別発注を勧めない(`rules/監査の型.md` の作法 — 全ての Opus・Fable の型の共通の作法)。
6. 親は発注文の冒頭に「粒度: 族 … をまとめて 1 体 / 合同監査 … 稿」を 1 行書いてよい(任意)。締めの報告では、起動した体の本数と、まとめられたのに分けた発注があったかを「手順の無駄」に書く。
7. **すぐ出せる族は全て出す — 発注の待ち行列 `READY.md` と Stop フック(2026-10-19 ユーザー指示、全 G)**:経緯 — G4 でユーザーが「未発注でいますぐ発注できるものがあればすべて実施」を何度も指示していたので、指示が無くても棚卸しが毎回走るように、引き金を「親がターンを終えて止まろうとする瞬間」に置いた(時間で回さない — 何かが戻ったときだけ起こされるので無駄な起動が無い)。
   - 各 G(サブテーマ・レーンを持つ G はその (研究ノート: `_orders`))は (研究ノート: `READY.md`)(雛形 `rules/templates/READY.md`、書き換え型)に族ごとに 1 行で状態 `ready`(今すぐ出せる)/ `running`(発注名・稿)/ `blocked`(待つもの)/ `defer`(出さない理由)を持つ。
   - **起動**:SessionStart フック `session-start-id.sh` が表示する session_id で `python (研究ノート) claim <_orders の路> <session_id> [レーン]`(ALL 型の親はレーンなし、レーン担当はレーンつき)。前のセッションが置いた旗 (研究ノート: `NO_NEW_ORDERS`) は消す。
   - **回収のたび**(体・ジョブが戻るたび):塞いでいたものが解けた行を `ready` に上げ、報告の残タスクを族にまとめて足し、`ready` を全て発注して `running` に書き換える。規律(族単位・合同監査・類 C を先に・同時起動の上限)はそのまま — 上限に達した G は `blocked(上限)`、小さな項目は族にまとめてから 1 行にする。
   - **Stop フック `require-ready-empty.sh`**:登録したセッションがターンを終えるとき、`ready` の行が残っていれば終了を止めて一覧を返す(表を直さずに続けて止まろうとしたら 1 回で素通り)。旗 `NO_NEW_ORDERS` があれば何もしない。
   - **締め**(時間枠の終わり・「新規発注を止めて」・週次枠の締め):旗 (研究ノート: `NO_NEW_ORDERS`)(中身は日付と理由 1 行)を置き、`ready_claim.py release`。表は次のセッションのために最新に書き換えて残す(旗は次のセッションの開始で消す)。
   - フックを読まないエージェント(他のエージェント など)は同じ手順を手で守る。脱出口は `CLAUDE_SKIP_READY_CHECK=1`。
   - **補充のサイクル(2026-10-19 ユーザー指示、G4 で永続)**:旗 (研究ノート: `AUTO_REPLENISH`) を置いた G では、ready が尽きて稼働中の体が少ない(既定 2 本以下)とき、Stop フックが「計算ジョブ以外でいま着手できる手の洗い出し → 監査の型 1 体の一度きりの独立監査 → 判定 OK・FIX の行の全着手」を指示する(冷却 3 時間、手順の正本は G4 `CLAUDE.md` §4 と (研究ノート: `_TEMPLATE_replenish.md`))。いまは G4 だけが旗を置く — 他の G に広げるのはユーザーの指示があるときだけ。

## 研究の型(2026-10-14 ユーザー指示。G4 で確立した運用を全 G・全テーマ・全エージェントに適用)

G4(純 QED₄)の 2026-10-12〜14 の運用で、残り台帳の本数が実際に減った手順を標準にする。上の「進捗の指標と並列度の規律」の具体化。細則は (研究ノート: `G共通_セッション手順.md`)、雛形は `rules/templates/STATUS.md`。

1. **STATUS が現在地の正本**: 主標的ごと(レーンがあればレーンごと)に `STATUS*.md` を持ち、毎チェックポイントで全面書き換え(8KB 上限)。固定の節:1 行目「残り台帳:行・類 C・類 B・類 A の本数」と設計やり直しの記録 / 台帳の各行(名指し・類・閉じた方式の F 番号・当てている体)/ 推移の 1 行(増減と理由)/ 運用の決定 / 閉じたもの / 作業中 / 次の 3 手(層の印と成算 ID)/ 番号(次の稿・成算・発注・PROVED/FAILED)。BOOT.md は事実表・罠・ファイルマップ・運用規則に絞り、めったに変えない。行の内側(塊・句)が多くて 8KB に収まらない律速の行は、内側を `<レーン>_塊台帳.md`(書き換え型、16KB 上限、STATUS と同時に書き換え)に分け、STATUS には行と塊の 1 行要約だけを置く(2026-10-19 ユーザー承認;G4 S39 で STATUS_R2 の短縮が 15 回ほど要り、取り違えを 1 件生んだ)。更新時刻は書く直前に `date` で取る。
2. **番号帯**: 同じ台帳を複数のセッション・レーンが同時に書くときは、PROVED・FAILED・稿・成算 ID・発注名の番号帯を分ける(例 G4 `LANES.md` §3)。共有台帳(NUMERICS_FACTS など)は push の直前に採番し、衝突したら両方を残して自分の行を最大 +1 に振り直し、その番号を引く発注文・稿・稼働中の体(`SendMessage`)も直す。
3. **発注の型**(必須節は 7.・8. と既解決の確認のとおり):任務は起動前に固定した判定文で書く。類 C の kill-check は `書き下しの型`・予算 2〜3 時間・worklog が判定の正本。書き下しは `書き下しの型`(2026-10-15 ユーザー指示:監査の型 は監査だけ)・予算 4〜8 時間で、任務の先頭に「(0) 類 C を先に — 否定なら書き下しに進まず報告」を置く。報告の 1 行目は推奨。発注文を書いたら同じ手で起動し、STATUS の作業中に足す。
4. **連結の道具**: 断片の連結・採番・処方の適用・監査記録の差し込みは (研究ノート: `ledger_link.py`)(番号帯 `--band`・成算の接頭辞 `--seisan-prefix`、処方は全組を照合し未適用が残れば止まる)。verifier-backed の稿への反映は冒頭の訂正注記の 1 行だけで、(研究ノート: `header_note.py`) を使う。
5. **監査の追加規律**:
   - 監査人が穴を塞ぐために自分で書いた補題は self-audited 扱い。S1 と合わせて、別の体による独立確認(作成者の論法を写さず導き直す)を出す。
   - 長く停滞した行を閉じるという大きな主張の S2 では、「難しさの保存の検査」を最重点にする。閉じた方式を止めていた障害がどの項に移ったかを特定し、それが本当に払われるかを示させる。名指しの無い仮定や設計値の不等式に隠れていれば反駁。
   - candidate の稿に依って他の稿へ付ける注記・処方は、その S2 が通るまで (研究ノート: `_hold`) に保留する。
   - **閉鎖の数え方(2026-10-19 ユーザー承認)**:名指しの句を「閉じた(−1)」と STATUS の現在地・推移に書くのは、合同 S2 がその句の難しさの移り先を特定してから。それまでは「候補(S2 待ち)」の札をつける。推移の行では「消滅」(難しさが本当に払われた)と「他の行・入力への移し」を分けて書き、移し先の行の類を見直す(経緯:G4 S39 で親が書いた −1 のうち 3 件が S2 で戻った — 値の閾値の取り違え・典型の背景での値・狭い定義)。
6. **設計のやり直し(テンプレート C)の追加**:
   - 停滞した方式の**共通点**を 1 行で特定してから、新しい十分条件を立てる(例:「全尺度を 1 度に評価していた」)。
   - **消費者の側を先に照合する**。供給側の命題を強める前に、それを使う定理が実際に要る強さ・範囲・形(sup か平均か、全ての配位か小場だけか、対数凹か分散か、どの σ-代数で条件づけるか)を字面で確かめる。G4 では、13 本の方式が閉じた行が「消費者が要らない強さを求めていた」と特定して閉じ(#3069)、別の行では「消費の形」が難所を作っていたと分かった(#3072)。
   - 設計メモは worklog に日付つきで残し、STATUS の 1 行目から指す。行の統合・分割をしたら、台帳の ± と理由を推移の行に書く。
7. **締めの報告**: 台帳の推移(開始 → 終了)に加え、本質的な難しさ(評価の本数そのもの、閉じた方式)と手順の無駄(衝突・事故・作法の逸脱・やり直し)を分けて書く。大きな進展の通知は verifier-backed になってから(下の節)。

## 大きな進展の通知(2026-10-06 ユーザー指示。(研究ノート: `04_研究`) 配下の全エージェント)

いずれかの G(または (研究ノート: `02_数学・物理`) のテーマ)で大きな進展があったら、区切りを待たずにユーザーへ通知する。自律運転中でも同じ。

- **通知する「大きな進展」**(どれか 1 つ。新しい主張は verifier-backed になり commit した時点で。self-audited・candidate では通知しない):
  1. 大目標の成功条件・終点命題の達成、または需要表(`需要_G<n>.md`)の行が閉じた。
  2. 難問台帳の行(HP-G<n>-k)・BOOT の開タスクの**本体**が解決または反証された。
  3. STATEMENT「標語 A の主定理」の追加・変更に当たる結果。挑戦問題が主力の成果になった。
  4. 達成度が 5 ポイント以上動いた。
  5. 負の進展: verifier-backed の主張・主定理・確定条文に誤りや抜け道が見つかった、または本線の方式が閉じた。
  6. ユーザーの判断が無いと先へ進めない設計上の分岐(承認必須事項で、委任では採れないもの)。
- **通知しないもの**: 個々の補題・稿の昇格、方式の 1 つの閉鎖、数値の PASS / INCONCLUSIVE、台帳の整理、巡の完了。これらはセッション報告と進捗ファイルで足りる(通知が多いと読まれなくなる)。
- **方法**: Claude Code は `PushNotification` ツール(一覧に無ければ ToolSearch で `select:PushNotification`)。1 件 1 通知、200 字以内・1 行・Markdown なしで、先頭に G と結論を書く。過大に書かない(限定つきの結果は限定を 1 句入れる)。ツールの無いエージェント(他のエージェント など)は、報告の 1 行目を「【大きな進展】G<n>: …」で始め、セッション報告の冒頭にも同じ行を置く。
- **誰が**: ワーカー・監査者・代行リード(サブエージェント)は通知せず、報告の 1 行目に「【大きな進展】G<n>: …」と書く。親が台帳の行で照合してから通知する。
- 通知した事象は、その G の BOOT 現在地とセッション報告に同じ 1 行で残す(通知だけで終わらせない)。

## (研究ノート: `01_新井プログラム継承`) の追加義務(この配下で優先)

この配下では上の共通規則に加えて次を守る。大目標駆動の運用(G 宣言・並列実行・チェックポイント)は同フォルダの `CLAUDE.md` と (研究ノート: `ROADMAP.md`) 第 V 部。この節は同配下に限り「総括の書き換えは大きな節目だけ」という BOOT の通常規則より優先する。

1. 進捗ファイル: 実体は G 別ファイル (研究ノート: `G<n>.md`)(担当 G だけが書く)。`00_進捗総括.md` は索引と横断的結論だけで、大きな節目にだけ更新する(1 ファイルに全 G が書くと追記が消える)。
   - 更新はセッション終了時だけ(昇格の正本は PROVED)。達成度ファイルは 5 ポイント以上動いたときだけ。日々の引き継ぎは BOOT.md に一本化する。
   - 書き換え型(2026-10-04〜): 最新の状況だけを雛形どおりに全面書き換えし、履歴は書かない(書式は同フォルダ `CLAUDE.md` §4)。成果が無くても、閉じた方針や現在の障害を反映する。
   - 完了判定の前に `git diff` を見て、担当 BOOT.md か (研究ノート: `G<n>.md`) に差分が無ければ完了扱いにしない。
2. 成果候補への敵対的セルフレビュー: 新規の定理・補題・反例・計算則・漸近則・既存論文の訂正などの成果候補は、`PROVED.md` / `NOVEL.md` への昇格と進捗への確定記載より先に、反証専任のセルフレビューを 1 ラウンド受ける。
   - 最低限、量化子・定義域・well-definedness・符号と共役・境界例と退化例・最小反例・既知結果から直ちに従う部分・新規性の重心・数値実験が実際に検証する範囲を点検する。
   - 「主張を壊す」立場で、小さい有限模型・極端なパラメータ・既知命題への還元を先に試し、反例・穴・過大な枠付けは修正前後が分かる形で記録する。
   - 結果はテーマの `EVIDENCE.md`(または既存の命名規則に沿う記録)に、各指摘の判定・根拠・修正先・修正内容・残る留保を明示して残す。棄却した主張は `FAILED.md` へ。
   - 通過だけでは `self-audited`。`verifier-backed` には独立監査が要る(明確な昇格候補だけ、体数の上限なし)。
   - 数値検算は解析的証明の代替にしない。有限模型が無限次元性・稠密性・極限を検証できないときは、その限界を成果物と進捗に明記する。
